# Extending the task: add your own tool

The fastest way to understand this codebase is to add a sixth tool. Nothing here is generated by magic: the system prompt is built from the Pydantic models, the data generator is hand-written per tool, and the evaluator picks everything else up from the schemas. This page walks the five touchpoints and the count arithmetic that trips people up.

Worked example: a `delete_namespace` tool that removes a Kubernetes namespace.

---

## 1. The schema (the contract)

`src/schema.py`. Add the parameters, the call envelope, and register both:

```python
class DeleteNamespaceParams(StrictModel):
    namespace: str = Field(description="Kubernetes namespace to delete (e.g. staging-tmp)")
    force: bool = Field(default=False, description="Delete even if resources remain")


class DeleteNamespaceCall(StrictModel):
    tool: Literal["delete_namespace"]
    parameters: DeleteNamespaceParams
```

Then add `DeleteNamespaceCall` to the `ToolCall` union and the name to `PARAM_MODEL_MAP`:

```python
class ToolCall(RootModel[Annotated[
    Union[DeleteNamespaceCall, DeployServiceCall, RestartPodCall, RollbackDeploymentCall,
          ScaleClusterCall, NoActionCall],
    Field(discriminator="tool"),
]]): ...
```

That is the whole schema change. `build_system_prompt()` iterates `PARAM_MODEL_MAP`, so the system prompt, the strict parser, `show-mask`, and the evaluator's schema check all follow automatically — the instructions and the validator cannot drift apart, which is one of the design properties this repo is proudest of.

**Optional parameters matter.** Any field with a default becomes an "omitted default" case: the model must write it explicitly, and `normalized_match` exists to catch the difference. Give a tool at least one optional field if you want it to exercise that path.

## 2. The generator (the data)

`src/generate_data.py`. Write a function with the same shape as `deploy`/`restart`: choose entities from the pool, decide which optionals are omitted via `_choose_state(rng, omit_p)`, then return `(prompt, params, omitted)` with **four phrasing families** (train uses 0–1, validation 2, test 3 — that is the wording-generalization axis):

```python
def delete_namespace(rng, pool, family, omit_p):
    namespace = rng.choice(pool.namespaces)
    force = _choose_state(rng, omit_p)
    base, phrases = (
        (f"Delete the {namespace} namespace.", (" Force it if resources remain.", " Only if it is empty.", " Remove it.")),
        (f"Tear down namespace {namespace}.", (" Hard delete.", " Refuse if anything is left.", "")),
        (f"Remove the {namespace} namespace from the cluster.", (" Force deletion.", " Check it is empty first.", "")),
        (f"Clean up {namespace}.", (" Delete everything in it.", " Leave the contents alone.", "")),
    )[family]
    prompt = base + phrases[{True: 0, False: 1, None: 2}[force]]
    params = {"namespace": namespace, "force": bool(force)}
    return prompt, params, ["force"] if force is None else []
```

Register it and keep `ACTION_TOOLS` in sync — the challenge sets use that tuple:

```python
TOOL_GENERATORS = {..., "delete_namespace": delete_namespace}
ACTION_TOOLS = ("deploy_service", "restart_pod", "rollback_deployment", "scale_cluster", "delete_namespace")
```

Add the entity pool you used (`SEEN.namespaces`, and an unseen counterpart in `UNSEEN`) to `EntityPool` and both pools. Unseen entities are what make `challenge_entities` a real transfer test.

**Grounding is enforced by tests.** `tests/test_core.py::DatasetTests::test_regenerated_data_is_reproducible_disjoint_and_grounded` checks that every non-default string value in the target appears verbatim in the prompt, and that omitted fields carry exactly the schema default. If your generator paraphrases a value (e.g. writes `prod` for `production`), the test tells you.

## 3. The count arithmetic (the part people miss)

Splits are built **balanced across tools** by round-robin, and the tests assert it. With N tools, each split size should divide evenly by N:

| Split | Current (5 tools) | With 6 tools |
|---|---|---|
| `train` | 250 → 50 per tool | use 252 → 42 per tool (or accept imbalance and update tests) |
| `valid` | 50 → 10 per tool | 48 → 8 per tool |
| `test` | 75 → 15 per tool | 72 → 12 per tool (or 90 → 15) |
| `challenge_entities` | 40 → 10 per action tool | 40 → 8 per tool (5 action tools) |
| `challenge_defaults` | 40 → 10 per action tool | 48 → 8 (if you add the new tool to `ACTION_TOOLS`) |

Update `build_splits` accordingly, then:

```bash
uv run python main.py prepare      # regenerates every split, deterministically
uv run python main.py show-data    # balance, families and omitted counts at a glance
```

`show-data` is the fast feedback loop here: it shows `6 × 42` in the Tools column when the split is balanced, and the families column tells you the wording axes are still separated.

## 4. The tests

Run the core suite first — it is seconds, not minutes:

```bash
uv run python -m unittest discover -s tests -p "test_core.py" -v
```

Expect to update:

* `test_split_design` — split sizes, per-tool counts, and the tool list for challenge sets.
* `test_regenerated_data_is_reproducible_disjoint_and_grounded` — it iterates whatever you registered, so it passes automatically *if* your values are grounded.
* Any test that asserts a five-entry tool list or a fixed `test` size.

Then the full suite (`uv run python -m unittest discover -s tests -v`) and lint (`uv run ruff check .`).

## 5. Everything downstream is automatic

Nothing else changes. Worth confirming once, because it is the point of the design:

* `main.py eval` scores the new tool, adds a row to the per-tool table, and includes it in the failure taxonomy.
* `main.py show-params` unchanged (it counts projections, not tools).
* `main.py inspect` will trace a decode that emits the new tool.
* `main.py ablate` unchanged — and a rank ablation is a good sanity check that the new tool does not dominate the loss.
* The plots (`eval_comparison.png`, `challenge_comparison.png`) scale their x-axis labels from the data.

## 6. If your tool should *not* exist

A tool the model must refuse is data, not schema: add a phrasing to `UNSEEN_UNSUPPORTED` in `src/generate_data.py` so `challenge_abstain` covers "someone asks for something we deliberately do not do". That is how the repo tests abstention generalization — new kinds of unsupported request, never seen in training.
